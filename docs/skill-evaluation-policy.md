# Evidencecraft Skill 验收政策

状态：`ACTIVE — RISK-CALIBRATED`

本文决定创建或修改 Skill 时需要多少验证。目标是发现真实行为错误，不把测试流程变成主要
工作量，也不因追求低成本而压缩职责所需的正文和配套资源。

## 1. 默认原则

1. 先做便宜、确定性的检查，再决定是否调用模型。
2. 测试实际改变的 Trigger、判断权、产物或交接，不重跑无关矩阵。
3. 不用同一 prompt 的重复次数代替不同风险覆盖。
4. 一个场景可以同时验证触发、fresh context、产物和交接。
5. 出现关键失败立即停止、修复，再只重跑失败边界和最近邻回归。
6. routine 测试输出留在临时目录，不把 `evals/`、transcript 或大日志提交到仓库。

## 2. 先判断是否需要独立 Skill

候选应同时具备：

- 普通用户语言可以识别的独立 Trigger；
- 一个不能安全留给主 Agent 或相邻 Skill 的主要判断权；
- 独立说明能降低重大失败、上下文污染或恢复成本；
- 可观察结果、完成证据和 Return Route。

格式转换、模板填充、固定检查、背景知识、少量路由或尚无消费者的对象模型，优先使用普通
prompt、Reference、模板、脚本或 Harness 规则。

no-Skill baseline 不是普通 Skill 的默认门。只有候选用于改变自然行为、执行停止纪律，或
无法判断问题来自基础模型、候选 Skill、Harness 还是测试 prompt 时，才做一次最小 control。

## 3. 结构与规模检查

Skill 必须有 `SKILL.md`，但不规定只能有单文件。先与对应 Superpowers Skill 的职责深度和
配套模式比较，再确认：

- 目录名、`name` 和 description 合法；
- frontmatter 只包含当前平台支持的字段；
- description 能区分自然正例和最近邻负例；
- 正文完整承载核心流程、判断权、停止/完成门、结果和 Return Route；
- 高频入口比复杂流程更短；复杂 Skill 可以接近当前 `skill-creator` 的渐进披露上限；
- 详细知识放在一层 Reference，稳定输出格式放在 template/asset，独立角色契约放在 prompt，
  确定性重复操作放在 script；
- 正文、prompt、Reference、template、script、asset 或 metadata 各有独立职责和明确调用方；
- 正文说明何时读取或调用配套资源，配套之间不深层跳转、不重复同一规则；
- 没有 README、安装指南、测试历史、空目录、重复规则或 fixture 细节；
- 没有硬编码 Harness、模型、本机路径或秘密。

正文长短和配套文件数量本身不判定通过或失败。重要流程被删减是缺陷，无调用方的配套同样是
缺陷。使用当前 `skill-creator` 提供的 `quick_validate.py`，再按第 5 节验证实际配套。

## 4. 测试层级

### L0：静态检查

适用于所有改动：

- `quick_validate.py`；
- 链接、相对路径和必需文件；
- frontmatter 与目录一致；
- 正文和 Reference 不矛盾、不重复；
- `git diff --check` 和完整 Diff 审阅。

纯文档、拼写、链接、非行为 Reference 和机械格式修改只做 L0，不调用模型。

### L1：两个行为场景

新 Skill、Trigger 或行为变化默认只运行：

1. 一个自然正例：应触发并产生主要结果；
2. 一个最近邻负例：不应执行该 Skill，也不得污染相邻任务。

场景使用新上下文、最小真实输入和自然用户措辞。不要向验证 Agent透露预期答案、已知 bug
或实现意图。

### L2：风险扩展场景

只有 Skill 涉及状态、路由、停止纪律、审查、跨 Skill 交接、阻断恢复、委派或高影响判断时，
才在 L1 之外选择一个最能改变设计或发布决定的扩展：

1. **无 Skill baseline**：用于确认基础 Codex 是否自然违反候选要纠正的纪律，或隔离候选、
   Harness 与测试 prompt 的责任；
2. **组合场景**：用于同时覆盖最重要的两个到三个状态或交接风险，例如：

- 正常状态与一个阻断 Return Route；
- 产物被下游 fresh context 正确消费；
- current 定义存在时正确跳过；
- 工作 Agent 返回后主 Agent 验证真实结果。

baseline 若已经表现正确，停止针对该行为扩写 Skill，不重复运行以制造 RED。普通 Skill 最多
2 个模型场景；选择一种风险扩展时最多 3 个；只有归因风险和交接风险都需独立决策时才同时
运行 baseline 与组合场景，此时最多 4 个。角色 prompt 的独立调用若未被这些场景覆盖，也计入
同一上限。预计超过 4 个前，先说明每个额外场景会改变什么设计或发布决定，并取得用户同意。

不采用 Superpowers `writing-skills` 的默认 5+ 次重复 micro-test。概率稳定性、措辞方差或
跨模型研究必须由用户另行授权，不能成为普通 Skill 的完成门。

### 流程集成

不要为每个 Skill 重复端到端测试。一组相邻 Skills 完成后运行：

1. 一次首次设置流程；
2. 一次正常周期复用流程。

多智能体故障注入、跨模型比较、概率稳定性和长周期漂移属于单独研究，不是单 Skill 完成门。

## 5. 配套资源验收

配套资源按实际风险验证，不因存在文件就增加一整套模型测试：

- **角色 prompt**：用一次 fresh-context 真实调用验证输入隔离、职责边界和输出契约；若已经
  在 L1/L2 场景中被真实调用，不重复测试；
- **Markdown template/asset**：用代表性输入填充或 dry run，确认能形成完整、可读、可继续
  交接的产物，不要求为每个字段单独调用模型；
- **script**：实际运行一个代表性成功输入和一个代表性失败输入；同类脚本可抽样，但必须说明；
- **纯知识 Reference**：检查链接、读取条件、与正文的一致性和重复内容；不改变行为时到静态
  检查即可停止；
- **agents metadata**：确认名称、简介和 default prompt 与最终 `SKILL.md` 一致。

## 6. 失败与早停

- 正例或负例关键失败：停止当前候选，不继续跑其他场景。
- 修复后先重跑失败场景；若修复可能影响另一边界，再重跑一个最近邻场景。
- 已有清楚、可复现的真实失败时直接复用，不重新制造多次 RED。
- 不为达到固定数量继续运行已经明确通过或失败的候选。
- 超时、工具失败和隔离失败记录在任务结果中，但不伪装成行为失败或通过。

## 7. 测试环境与记录

行为验证使用当前 Codex。记录实际模型/Harness、Skill hash、场景、结果和限制。Codex 不可用
时记录 `BLOCKED`，不改用 Claude Code、GLM 或其他模型替代。

默认记录位置是当前任务结果或 commit message。临时 prompt、输出和日志在验收后清理。只有
以下情况才另行设计持久评测存储，并由用户明确授权：

- 对外发布声明；
- 安全、合规或高影响审计；
- 需要概率或跨 Harness 研究；
- 失败证据必须供多人长期复核。

即使需要正式证据，也优先保存紧凑 manifest、prompt、score、代表性 final 和 raw-output
hash；大原始流放不可变外部存储，不复制成数百个仓库文件。

## 8. Schema 与其他额外产物

JSON Schema 不是 Skill 验收项。只有同时具备稳定跨运行语义、真实机器消费者、经过实际流程
稳定的字段，以及同一里程碑的 validator/迁移负责人时，才单独提议。

Reference、prompts、scripts、assets、agents metadata 和示例可按对应 Superpowers 的职责模式
创建，但必须有实际调用方；不能为追求同构而复制。兼容桥仍需真实版本迁移消费者。

## 9. 完成声明

完成时只报告：

- 创建前研究了哪些 Superpowers Skills，以及借鉴/不照搬什么；
- Skill 的 Trigger、判断权、结果和 Return Route；
- 实际新增的文件、各自调用方，以及为什么与职责复杂度相称；
- 执行了哪些 L0/L1/L2 检查；
- 跳过了什么及原因；
- 已知限制和下一次升级测试的明确触发条件。

不要只说“所有测试通过”，也不要为完成声明再创建一份仓库文档。
